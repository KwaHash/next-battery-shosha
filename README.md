# 受付アシスト

電気工事生産性OSの**商社側（`shosha/`）**を Next.js で実装したものです。
電材商社（電池屋）の受付担当が、工事会社からの問い合わせを**1つの受信箱**で受け、
**根拠を出して**自動回答と人の回答を振り分けます。

工事会社側の [現場アシスト（next-battery-genba）](../next-battery-genba) と**同じ Supabase** を使います。
現場アシストで送られた材料の相談がこの受信箱に出て、ここで返した回答が現場アシストの
「回答が届きました」に戻ります。

---

## 動かす

### 1. 環境変数

```bash
cp .env.example .env.local
```

現場アシストと**同じ** Supabase プロジェクトの値を入れます。

| 変数 | 用途 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 接続先（genba と同じ） |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 受付担当のセッション。読み取りと、回答以外の書き込みは RLS を通る |
| `SUPABASE_SERVICE_ROLE_KEY` | **回答の送信と監査ログだけ**に使う。クライアントへ渡さない |

### 2. DB に追加分を入れる（初回のみ）

| TABLE | CONTENTS |
|---|---|
| `shosha_staff` | 誰が商社の受付担当か。ここに無い人は入れない |
| `model_aliases` | 型番の別名・後継品。人が直した結果が溜まる（**本体の資産**） |
| `answer_logs` | 回答の履歴。自動か人か・直したか・対応時間。**追記のみ** |
| `request_opens` | 受付担当が最初に開いた時刻（対応時間の起点） |
| `auth_shosha_tenant_ids()` | 上の3テーブルの RLS が使う |

### 3. 受付担当の登録

requests の RLS は genba 側の `memberships` で判定しているため、`shosha_staff` だけだと
受信箱が空になります（画面に警告が出ます）。

### 4. 起動

```bash
npm install
npm run dev
```

PC 幅で開いてください。受付は PC で使う前提です（狭い幅でも崩れません）。

## 画面

| 画面 | パス | 何をするか |
|---|---|---|
| **受信箱** | `/inbox` | 未回答・回答済・受注。判定（自動で返せる／人が確認／保安機器）と止まった理由。まとめて自動返信 |
| 問い合わせの処理 | `/inbox/[id]` | 判定の根拠・現場着日・相当品・下書きを直して返信・別名の登録・納期変更の通知 |
| 電話・FAXを起票 | `/new` | 会社・商品・数量の3項目で1件にする。旧型番でも商品が見つかる |
| 別名・後継品 | `/aliases` | 溜まった「聞かれた型番 → 正解」の一覧・登録・取り消し |
| 省人化の効果 | `/effect` | 自動回答率・人が直した率・対応時間・経路の内訳・週ごとの推移 |
| CSV 書き出し | `/export?kind=inquiries` / `?kind=aliases` | 全件。Excel でそのまま開ける（BOM 付き） |

## 実装で守っていること

### 回答はサーバでしか書かない

`ANSWERED` への遷移と `answer_*` は `lib/shosha/answer.ts` からしか書きません。
service role を使うのはここ（と監査ログ）だけです。呼ぶ前に、受付担当であることと、
その依頼が担当の取引先のものであることを `lib/shosha/actions.ts` で確かめています。

- **人の回答は `answer_mode: 'HUMAN'`** で書きます。これが genba の
  `answerRequestOnServer` が数える「人が承認した履歴」になり、**次の同じ型番が自動で返せる**
  ようになります（学習のループ）
- 書き込みは `status = 'SENT'` のときだけ。自動回答や別の担当者と同時に返しても二重になりません
- 「まとめて自動返信」は画面の判定を使わず、**サーバでもう一度5条件を通します**

### 判定は genba と同じ

`lib/domain/auto-answer.ts` は genba の同名ファイルと**同じ判定**です。**片方だけ変えないでください。**
画面ごとに「なぜ人が確認するのか」の説明が変わってしまいます。
保安機器は履歴があっても自動回答しません。

### 納期は「現場に着く日」で返す

`lib/domain/delivery.ts`。メーカー出荷＋自社物流（直送 +1日／拠点経由 +2日／キッティング +2日）
＋現場の受取条件。施工予定日の前日着を推奨し、間に合わない・早すぎるときは警告します。
返した現場着日は `delivery_promised` に残し、あとで納期が変わったら
`delivery_changed_to` で**その発注についてだけ**工事会社へ知らせます（genba の「納期が変わりました」）。

### 相当品は在庫が足りないときだけ

平時は出しません（商流を荒らさない）。**候補を出すところまで**で、確定は人です。
回答に入れた候補は `alternatives` に入り、genba の回答カード「相当品の候補」に出ます。

### 効果の数え方

- 回答件数は `requests` を正にします。genba のサーバが送信時に自動回答した分は
  `answer_logs` を書かないため
- 「人が直した率」は、画面が最初に出した下書きと送った本文の差で判定します（空白の違いは数えない）
- 対応時間は「最初に開いてから返すまで」。放置時間で平均が壊れないよう **60分で頭打ち**。
  開いた記録が無い回答は「測れていない」として平均から外します
- 従来の電話・FAX対応 **12分は仮値**です。実測に置き換えてください

### そのほか

- 全業務データに `tenant_id`。分離は RLS で行い、画面の if 文では隠さない
- 監査ログは追記のみ。**拒否した操作も `DENIED:` 接頭辞で残す**（自動回答で止めた理由も）
- 別名・後継品と回答の履歴は物理削除できない（DB トリガー）。取り消しは `archived_at`
- CSV は、`=` などで始まる値を文字として書き出す（Excel の式として実行させない）
- 日付は Asia/Tokyo 固定（`lib/domain/clock.ts`、genba と同じ）

## 確かめていないこと（genba 側の DB を見て確認してください）

このリポジトリには genba 側のスキーマ（SQL）がありません。次を前提にしています。

| 前提 | 外れていたら |
|---|---|
| `guard_request_answer` は service role による `answer_mode: 'HUMAN'` の書き込みを通す | 人の回答が保存できません。トリガーに HUMAN の扱いを足してください |
| `requests` の RLS は、`memberships` があるユーザーの INSERT／UPDATE を通す | 電話の起票・納期変更の通知が失敗します（画面にエラーが出ます） |
| `requests.channel` は `PHONE`／`FAX`／`MAIL` を受け付ける | 起票が失敗します |
| ID は uuid | 入力の検証（zod）で弾かれます |
